## What I Explored Today

Today I dug into how compiler optimization flags—specifically `-O2` and `-Os`—behave in an automated CI pipeline for embedded firmware. I’ve always treated these flags as a “set and forget” in my Makefiles, but after a production bug where a timing-critical ISR broke under `-O2` (and worked fine under `-O0`), I realized I needed to understand the tradeoffs systematically. I spent the day building a CI job that compiles the same firmware with both flags, runs static analysis, and compares binary size and stack usage—so we can catch regressions before they hit hardware.

## The Core Concept

Compiler optimization flags are not just about speed vs. size—they fundamentally change the generated assembly. For embedded systems, this matters because:

- **`-O2`** enables aggressive inlining, loop unrolling, and instruction scheduling. It assumes the code is correct and the hardware is predictable. This can break code that relies on precise timing, volatile access patterns, or undefined behavior (like signed integer overflow).
- **`-Os`** prioritizes code size reduction. It disables some inlining and unrolling that increase size, but still applies most safe optimizations. It’s often the default for flash-constrained MCUs (e.g., Cortex-M0 with 32KB flash).

In a CI pipeline, the key insight is: **you must test with your release optimization flag, not just debug flags**. Many teams compile only with `-O0` or `-Og` in CI because it’s faster, then ship with `-O2` or `-Os`—and discover bugs only during hardware validation. The fix is to add a dedicated “release build” stage in your pipeline that uses the exact flags you’ll ship.

## Key Commands / Configuration / Code

Here’s a practical CI job (GitHub Actions YAML) that compiles firmware with both `-O2` and `-Os`, then compares the results:

```yaml
# .github/workflows/release-build-check.yml
name: Release Build Check
on: [push, pull_request]

jobs:
  optimization-check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Install ARM GCC toolchain
        run: |
          sudo apt-get update
          sudo apt-get install -y gcc-arm-none-eabi

      - name: Build with -O2
        run: |
          make clean
          # Override CFLAGS to use -O2, keep all other flags
          make CFLAGS="-O2 -mcpu=cortex-m4 -mthumb -Wall -Werror" \
               TARGET=build/o2_firmware.elf 2>&1 | tee build_o2.log
          # Extract code size from .elf
          arm-none-eabi-size build/o2_firmware.elf > build_o2_size.txt

      - name: Build with -Os
        run: |
          make clean
          make CFLAGS="-Os -mcpu=cortex-m4 -mthumb -Wall -Werror" \
               TARGET=build/os_firmware.elf 2>&1 | tee build_os.log
          arm-none-eabi-size build/os_firmware.elf > build_os_size.txt

      - name: Compare sizes and flag differences
        run: |
          echo "=== -O2 size ==="
          cat build_o2_size.txt
          echo "=== -Os size ==="
          cat build_os_size.txt
          # Fail if -O2 binary is smaller than -Os (suspicious)
          O2_SIZE=$(awk '/\.text/{print $1}' build_o2_size.txt)
          OS_SIZE=$(awk '/\.text/{print $1}' build_os_size.txt)
          if [ "$O2_SIZE" -lt "$OS_SIZE" ]; then
            echo "WARNING: -O2 binary is smaller than -Os! Check for dead code elimination."
            exit 1
          fi
```

For a more thorough check, I also add a static analysis step that compares stack usage (requires `-fstack-usage` flag):

```makefile
# In your Makefile, add a target for stack analysis
stack-check: $(TARGET)
	arm-none-eabi-objdump -d $(TARGET) > $(BUILD_DIR)/disasm.txt
	# Parse stack usage from .su files (generated by -fstack-usage)
	python3 tools/check_stack.py --max-stack 512 --su-files $(BUILD_DIR)/*.su
```

The Python script `check_stack.py` can be a simple grep that warns if any function’s stack usage exceeds 80% of your configured limit.

## Common Pitfalls & Gotchas

1. **`-O2` can hide volatile bugs.** If you forget `volatile` on a memory-mapped register or a flag shared between ISR and main loop, `-O2` might optimize away the read. The code works in debug, fails in release. Always run a `-O2` build with `-Wvolatile` (GCC 12+) or at minimum `-Wall -Wextra`.

2. **`-Os` is not a subset of `-O2`.** They enable different optimization passes. For example, `-Os` may inline a small function that `-O2` would not, because inlining reduces call overhead but increases size. Always test both—don’t assume one is “strictly better.”

3. **Timing changes are not caught by CI.** A CI pipeline can’t measure real-time behavior. If your firmware has tight loops or delay loops, `-O2` may execute them faster, breaking UART baud rate generation or software timers. Mitigate by adding a `-O2` build that runs on an emulator (e.g., QEMU for Cortex-M) and checks that a GPIO toggles at the expected frequency.

## Try It Yourself

1. **Add a dual-optimization build to your CI.** Modify your existing pipeline to compile with both `-O2` and `-Os`. Use `arm-none-eabi-size` to compare `.text` section sizes. Set a threshold: if the size difference is >20%, flag it for review.

2. **Enable `-fstack-usage` and parse the output.** Add `-fstack-usage` to your CFLAGS for one build. Write a small script that finds the function with the highest stack usage and compares it against your MCU’s SRAM size. Fail the build if any function exceeds 80% of available stack.

3. **Test with `-Werror` and `-Wall` for both flags.** Run `make CFLAGS="-O2 -Wall -Werror -Wvolatile"` and fix any warnings. Then repeat with `-Os`. You’ll likely find at least one warning that only appears under one optimization level (e.g., “uninitialized variable” that the compiler only detects with certain inlining).
