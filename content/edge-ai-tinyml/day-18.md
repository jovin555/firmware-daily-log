## What I Explored Today

Today I dug into the hardware acceleration options available on modern Cortex-M and Cortex-M55/M85 MCUs for neural network inference. Specifically, I compared the Cortex-M55's MVE (M-Profile Vector Extension, aka Helium) with the Ethos-U55 NPU (Neural Processing Unit) found in Arm Corstone-300 and similar platforms. I wanted to understand when each matters, how CMSIS-NN leverages them, and what a practical migration path looks like from pure CPU inference to hardware-accelerated inference.

## The Core Concept

The fundamental bottleneck in MCU inference is the multiply-accumulate (MAC) operation. A single 3x3 convolution on a 32x32 feature map with 16 channels requires ~73,000 MACs. Without acceleration, each MAC is a load-multiply-add-store sequence on the CPU. MVE and Ethos-U attack this differently:

- **MVE (Helium)** is a SIMD vector extension that processes 4x 16-bit or 8x 8-bit operations per instruction. It's a general-purpose accelerator—you get it on any Cortex-M55 or M85, and it accelerates any vectorizable loop, not just neural networks. CMSIS-NN uses MVE intrinsics to unroll convolution loops, achieving 4-5x speedup over scalar code.

- **Ethos-U** is a dedicated NPU with a weight decoder, streaming data path, and dedicated MAC array. It's a coprocessor: you send it a command stream (tensors, weights, layer parameters), and it returns the output tensor. The CPU is freed during inference. Ethos-U can achieve 10-100x throughput improvement over CPU-only, but it requires specific hardware and a custom driver stack.

The key insight: MVE is *always available* on M55/M85 and requires no extra silicon. Ethos-U is a *separate IP block* that must be integrated into the SoC. If you're designing a product, MVE is the baseline; Ethos-U is the upgrade for latency-critical or high-throughput applications.

## Key Commands / Configuration / Code

### 1. Checking MVE Availability at Compile Time

CMSIS-NN uses preprocessor defines to select the optimal kernel. You should never write MVE intrinsics directly—let the library handle it.

```c
#include "arm_nnfunctions.h"
#include "arm_nnsupportfunctions.h"

// CMSIS-NN automatically selects MVE path if __ARM_FEATURE_MVE is defined
// Your code stays the same:
arm_convolve_s8(input, input_dims, weights, weight_dims, bias, bias_dims,
                conv_params, output, output_dims);

// To verify MVE is being used, check the disassembly:
// arm_convolve_s8 calls arm_convolve_s8_mve() when MVE is enabled
```

### 2. Ethos-U Driver Initialization (Vela Compiler Output)

Ethos-U models are compiled with Arm's Vela compiler, which produces a `.tflite` binary and a C array of command stream data.

```c
// ethosu_driver.h from the Ethos-U core driver
#include "ethosu_driver.h"

// Global driver instance
struct ethosu_driver ethosu_drv;

// Initialize the NPU (called once at boot)
void npu_init(void) {
    // Base address of Ethos-U registers (platform-specific)
    const uintptr_t base_address = 0x40000000; // Corstone-300 default
    
    // IRQ number for Ethos-U (platform-specific)
    const int irq_number = 56;
    
    ethosu_init(&ethosu_drv, base_address, NULL, 0, irq_number, NULL);
}

// Run inference with pre-compiled network
void run_npu_inference(const uint8_t *input_data, uint8_t *output_data) {
    // The network binary is generated by Vela
    extern const uint8_t network_model_data[];
    extern const uint32_t network_model_size;
    
    // Input and output tensor info from Vela output header
    extern const uint32_t input_tensor_size;
    extern const uint32_t output_tensor_size;
    
    // Run inference
    int ret = ethosu_invoke(&ethosu_drv,
                            (void*)input_data, input_tensor_size,
                            (void*)output_data, output_tensor_size,
                            network_model_data, network_model_size,
                            NULL, 0);
    if (ret != 0) {
        // Handle error (e.g., NPU timeout)
    }
}
```

### 3. Vela Compiler Command (for Ethos-U)

```bash
# Convert TFLite model to Ethos-U optimized binary
vela \
    --output-dir ./ethos_u_output \
    --system-config Ethos_U55_High_End_Embedded \
    --memory-mode Shared_Sram \
    --config my_vela.ini \
    model.tflite

# Outputs: model_vela.tflite (optimized), model_vela.h (C array)
```

## Common Pitfalls & Gotchas

1. **MVE is not a drop-in for all CMSIS-NN functions.** Some functions (e.g., depthwise convolutions with large channel counts) don't have MVE-optimized paths. Always profile your specific layers. I wasted a day assuming `arm_depthwise_conv_s8()` would use MVE—it only does for certain stride/dilation combinations. Check `arm_nnfunctions.h` for the `_mve` suffix on function declarations.

2. **Ethos-U memory alignment is strict.** The NPU requires 16-byte alignment for input/output buffers and 8-byte alignment for weight buffers. If you allocate with `malloc()` on a standard heap, you'll get alignment faults. Use `aligned_alloc(16, size)` or CMSIS-RTOS2's `osMemoryPoolNew()` with alignment attributes. I've seen teams spend days debugging silent data corruption from misaligned buffers.

3. **MVE and FPU share registers on Cortex-M55.** If you use both floating-point and MVE intrinsics in the same function, the compiler may spill registers, negating performance gains. CMSIS-NN avoids this by using only integer MVE. If you write custom MVE code, keep FPU operations in separate functions or use `__attribute__((target("arch=armv8.1-m.main+mve.fp+fp.dp")))` to control ISA selection.

## Try It Yourself

1. **Profile MVE vs scalar on Cortex-M55.** Take a simple 3x3 convolution with 8-bit inputs (e.g., 16 input channels, 32 output channels, 32x32 feature map). Compile with `-march=armv8.1-m.main+mve` and without. Measure cycle count using DWT_CYCCNT. Expect 3-5x improvement.

2. **Port a TFLite model to Ethos-U using Vela.** Start with a MobileNetV1 0.25 quantized model from TensorFlow Model Garden. Run Vela with the `Ethos_U55_High_End_Embedded` system config. Compare the `.tflite` file sizes—the Ethos-U version will be smaller due to weight compression.

3. **Measure CPU idle time during NPU inference.** On a Corstone-300 FVP (Fixed Virtual Platform), run a simple CNN on Ethos-U while toggling a GPIO pin. Use a logic analyzer or the FVP's cycle counter to measure how long the CPU is free. Compare to running the same network on CPU-only with CMSIS-NN.
