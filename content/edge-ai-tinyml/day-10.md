## What I Explored Today

Today I dug into the memory management backbone of TensorFlow Lite for Microcontrollers (TFLM): the **tensor arena**. This is a pre-allocated, fixed-size buffer that the interpreter uses for all intermediate tensor storage during inference. I learned how to size it correctly, what happens when you undersize it, and how to profile arena usage on real hardware. This is the single most common source of runtime failures when porting models to microcontrollers.

## The Core Concept

Unlike desktop or mobile TensorFlow Lite, which can `malloc` and `free` memory dynamically during inference, microcontrollers typically run bare-metal or under a real-time OS with no heap. TFLM solves this by requiring you to allocate a single contiguous block of memory—the **tensor arena**—before the interpreter is initialized. The arena must hold:

- All input, output, and intermediate tensors
- Scratch buffers for operator kernels (e.g., convolution im2col buffers)
- Internal interpreter bookkeeping structures

The arena is allocated once and never resized. If you undersize it, the interpreter will fail at initialization or during the first call to `Invoke()`. If you oversize it, you waste precious SRAM. The art is finding the minimum viable arena size for your model.

The arena is managed by a simple bump allocator internally: as tensors are allocated, a pointer advances through the buffer. When inference completes, the allocator resets to the start—no fragmentation, no free list. This is deterministic and fast, but it means you cannot hold references to intermediate tensors across multiple `Invoke()` calls.

## Key Commands / Configuration / Code

### Step 1: Let the interpreter tell you the minimum size

The most reliable way to determine arena size is to let TFLM profile it. On a host machine (Linux/macOS), compile and run this:

```cpp
#include "tensorflow/lite/micro/micro_interpreter.h"
#include "tensorflow/lite/micro/micro_mutable_op_resolver.h"
#include "path/to/your_model.h"  // generated by xxd or flatbuffer

constexpr int kTensorArenaSize = 200 * 1024;  // start with generous guess
alignas(16) uint8_t tensor_arena[kTensorArenaSize];

// Load model
const tflite::Model* model = ::tflite::GetModel(your_model_data);
tflite::MicroMutableOpResolver<10> resolver;
// Register ops here...

// Build interpreter with arena
tflite::MicroInterpreter interpreter(model, resolver, tensor_arena, kTensorArenaSize);

// Allocate tensors — this will fail if arena is too small
TfLiteStatus allocate_status = interpreter.AllocateTensors();
if (allocate_status != kTfLiteOk) {
    // Increase kTensorArenaSize and retry
}

// After successful allocation, query actual usage
size_t used_bytes = interpreter.arena_used_bytes();
printf("Arena used: %zu bytes\n", used_bytes);  // e.g., 45672
```

**On embedded target**, you can't easily iterate, so do this sizing step on your dev machine first.

### Step 2: Set the final arena size with margin

Once you know `arena_used_bytes()`, add 10-20% margin for safety:

```cpp
constexpr int kTensorArenaSize = 45672 + 5000;  // ~55 KB
alignas(16) uint8_t tensor_arena[kTensorArenaSize];
```

The 16-byte alignment is critical—ARM Cortex-M4/M7 SIMD instructions require it.

### Step 3: Verify on target with debug logging

On your MCU, enable TFLM debug logging to catch arena overflow at runtime:

```cpp
// In your project's micro_log.h or equivalent
#define TF_LITE_REPORT_ERROR(interpreter, ...) \
    printf(__VA_ARGS__); \
    printf("\n");
```

Then watch for messages like:
```
Failed to allocate tensor arena. Requested: 50000, Available: 45000
```

## Common Pitfalls & Gotchas

**1. Arena size must be known at compile time on bare metal.**
You cannot dynamically allocate the arena on most MCUs. Use `alignas(16) uint8_t tensor_arena[SIZE]` as a global or static local. If you try to use `malloc`, you'll likely hit heap fragmentation or out-of-memory.

**2. The arena holds *all* intermediate tensors simultaneously.**
Models with many branches (e.g., MobileNetV2 inverted residuals) allocate tensors for every layer at once. Don't assume tensors are freed between layers—they're not. The arena usage is the peak memory across the entire graph.

**3. Operator registrations affect arena size.**
Some ops (like `CONV_2D` with im2col) allocate large scratch buffers inside the arena. If you switch from a reference kernel to an optimized CMSIS-NN kernel, the scratch buffer size changes. Always re-profile after changing the op resolver.

**4. The arena is NOT used for persistent weight storage.**
Model weights are typically stored in flash (read-only) and are not copied into the arena. Only activations and scratch buffers live there. If you're running out of SRAM, check if you're accidentally copying weights into RAM.

## Try It Yourself

1. **Profile your current model:** Take any TFLM model you have, run the `arena_used_bytes()` snippet on your host machine, and record the minimum arena size. Then reduce the arena by 10% and confirm the interpreter fails at `AllocateTensors()`.

2. **Compare two op resolver configurations:** Register only the ops your model uses (via `MicroMutableOpResolver`) vs. registering all ops (via `AllOpsResolver`). Compare arena usage—you'll likely see a significant difference due to scratch buffer allocations.

3. **Stress test on target:** On your MCU, intentionally set the arena to exactly `arena_used_bytes()` (no margin). Run 1000 inferences in a loop. Check for latent memory corruption by verifying output tensor values against a golden reference.
