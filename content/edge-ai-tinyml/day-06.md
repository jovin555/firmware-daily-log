## What I Explored Today

Today I dove deep into the runtime architecture of TensorFlow Lite for Microcontrollers (TFLite Micro). After spending the first five days wrestling with model conversion and quantization, I wanted to understand what actually happens when the interpreter fires up on a bare-metal ARM Cortex-M4. I traced the execution path from `tflite::MicroInterpreter::Invoke()` down to the kernel dispatch, mapped the memory layout of the arena, and benchmarked the interpreter overhead on a STM32L4 board. The key takeaway: TFLite Micro is not a stripped-down TFLite—it's a completely different runtime designed for deterministic, single-threaded execution with zero dynamic allocation after initialization.

## The Core Concept

The TFLite Micro runtime is built around three architectural decisions that make it viable on microcontrollers with as little as 16 KB of RAM.

First, **no dynamic memory allocation after setup**. The `MicroInterpreter` constructor takes a pre-allocated tensor arena (a `uint8_t*` buffer) and a `MicroAllocator` that partitions it during `AllocateTensors()`. After that, every `Invoke()` call reuses the same memory—no `malloc`, no `new`, no heap fragmentation. This is critical for safety-critical systems where you cannot tolerate allocation failures mid-inference.

Second, **flatbuffers as the model format**. Unlike TFLite's Flexbuffers or Protocol Buffers, FlatBuffers allow zero-copy access to the model graph. The interpreter reads the serialized `.tflite` model directly from flash (or a memory-mapped region) without parsing or deserializing. This means the model can be stored in read-only memory, and the interpreter only needs RAM for intermediate tensors.

Third, **a two-level kernel dispatch**. The interpreter walks the FlatBuffer graph, and for each operator, it calls `GetRegistration()` to fetch a function pointer from a registration table. This table is populated at compile time via `MicroMutableOpResolver`. The resolver is intentionally not automatic—you must explicitly register every op your model uses. This eliminates dead code and keeps the binary size under 100 KB for most models.

## Key Commands / Configuration / Code

Here's the canonical initialization sequence for a TFLite Micro interpreter on an STM32:

```cpp
// Step 1: Include the runtime and op resolver
#include "tensorflow/lite/micro/micro_interpreter.h"
#include "tensorflow/lite/micro/micro_mutable_op_resolver.h"
#include "tensorflow/lite/schema/schema_generated.h"

// Step 2: Declare the model as a flatbuffer array (generated by xxd)
// Usually placed in flash via __attribute__((section(".rodata")))
extern const unsigned char g_model[];
extern const int g_model_len;

// Step 3: Define the tensor arena (static allocation, no heap)
// For a 32 KB RAM target, 20 KB is typical for the arena
constexpr int kTensorArenaSize = 20 * 1024;
alignas(16) uint8_t g_tensor_arena[kTensorArenaSize];

// Step 4: Create the op resolver and register only needed ops
tflite::MicroMutableOpResolver<10> resolver;  // max 10 ops
resolver.AddFullyConnected();                 // registers FC kernel
resolver.AddSoftmax();                        // registers Softmax kernel
// resolver.AddConv2D();                      // uncomment if needed

// Step 5: Build the interpreter
tflite::MicroInterpreter interpreter(
    tflite::GetModel(g_model),   // zero-copy model pointer
    resolver,
    g_tensor_arena,
    kTensorArenaSize
);

// Step 6: Allocate tensors (this partitions the arena)
TfLiteStatus allocate_status = interpreter.AllocateTensors();
if (allocate_status != kTfLiteOk) {
    // Handle error — arena too small or model malformed
    return -1;
}

// Step 7: Get input/output pointers
float* input = interpreter.input(0)->data.f;
float* output = interpreter.output(0)->data.f;

// Step 8: Run inference
memcpy(input, my_sensor_data, sizeof(float) * input_size);
TfLiteStatus invoke_status = interpreter.Invoke();
if (invoke_status != kTfLiteOk) {
    // Handle runtime error (e.g., misconfigured kernel)
    return -1;
}
// output now contains inference result
```

To inspect the arena layout after allocation, you can query the allocator:

```cpp
// Print memory usage (useful for debugging arena size)
const tflite::MicroAllocator& allocator = interpreter.allocator();
int used_bytes = allocator.used_bytes();
int available_bytes = kTensorArenaSize - used_bytes;
printf("Arena: %d/%d bytes used\n", used_bytes, kTensorArenaSize);
```

## Common Pitfalls & Gotchas

**1. Forgetting to register all ops.** If your model uses a `CONV_2D` but you only registered `FullyConnected`, `Invoke()` will return `kTfLiteError` with no clear message. The debug build prints the missing op name to `printf`, but release builds silently fail. Always run `interpreter.GetModelDetails()` or check the model's operator codes with `flatc --raw-binary model.tflite` before writing the resolver.

**2. Arena size miscalculation.** The arena must hold all intermediate tensors plus the allocator's internal bookkeeping. A common mistake is setting the arena to exactly the sum of tensor sizes. The allocator overhead is typically 1–2 KB plus alignment padding. Use the `used_bytes()` method after `AllocateTensors()` to measure actual usage, then add 10% headroom. On constrained targets, I've seen alignment waste 200+ bytes per tensor.

**3. Misaligned tensor arena.** The arena must be aligned to 16 bytes (ARM Cortex-M requires 8-byte alignment for `uint64_t` access, but TFLite Micro internally uses 16-byte alignment for SIMD-friendly kernels). Declaring `uint8_t g_tensor_arena[20000]` without `alignas(16)` can cause hard faults on Cortex-M4 when the interpreter tries to load 32-bit floats from misaligned addresses. Always use `alignas(16)` or place the buffer in a `.bss` section with proper alignment.

## Try It Yourself

1. **Profile arena usage.** Take your quantized model from Day 05, initialize the interpreter with a 10 KB arena, and call `AllocateTensors()`. Print `used_bytes()` and `available_bytes`. Increase the arena until allocation succeeds, then report the minimum arena size. Compare this to the sum of all tensor byte sizes from the model's `SubGraph` flatbuffer.

2. **Add a custom op registration.** Create a simple model that uses only `FullyConnected` and `Softmax`. Register them explicitly. Then modify the resolver to use `MicroMutableOpResolver<5>` but only register 2 ops. Verify that `Invoke()` still works. Then try registering an op that doesn't exist in the model—observe the error behavior.

3. **Measure interpreter overhead.** On your dev board, time `Invoke()` for 1000 iterations using a hardware timer (e.g., DWT cycle counter on Cortex-M). Then time the same model using a hand-rolled inference loop (no interpreter). Report the overhead percentage. On my STM32L476, the interpreter adds about 8% overhead for a 3-layer MLP—mostly from the graph traversal and tensor pointer resolution.
