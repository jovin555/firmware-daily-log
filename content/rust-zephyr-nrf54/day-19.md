## What I Explored Today

Today I dove into Arm TrustZone-M on the nRF54LM20, specifically how to partition firmware into Secure and Non-Secure worlds using Zephyr's TF-M (Trusted Firmware-M) integration, and how Rust code can live in both domains. The nRF54LM20's Cortex-M33 implements TrustZone-M with configurable SAU (Security Attribution Unit) regions, and I wanted to understand the practical steps to isolate cryptographic keys, secure boot, and application logic. I built a minimal example where a Rust-based secure partition handles AES-256 key storage and attestation, while the non-secure Rust application calls into it via secure function calls (SVC).

## The Core Concept

TrustZone-M splits the Cortex-M33 into two "worlds": Secure (S) and Non-Secure (NS). The hardware enforces that NS code cannot read S memory, S peripherals, or S interrupts unless explicitly allowed. On the nRF54LM20, this is critical because the radio, flash controller, and cryptographic accelerators are all security-sensitive peripherals. The key insight: you don't need to put your entire application in the Secure world. Instead, isolate only the assets that matter—keys, secure boot, firmware update verification—and let the bulk of your application run in NS. Rust's ownership model maps beautifully here: the Secure world "owns" the cryptographic keys and exposes a safe API via a veneer table, while the NS world borrows that capability through function calls. Zephyr's TF-M integration handles the SAU configuration and the secure interrupt routing.

## Key Commands / Configuration / Code

### 1. Enabling TF-M in Zephyr for nRF54LM20

In your application's `prj.conf`:

```kconfig
# Enable TF-M secure partition manager
CONFIG_TFM=y
CONFIG_TFM_ISOLATION_LEVEL=2
CONFIG_TFM_PROFILE_TYPE=profile_small

# Partition the flash: 0x10000000-0x1003FFFF for S, 0x10040000+ for NS
CONFIG_TFM_FLASH_LAYOUT_NS_OFFSET=0x10040000
CONFIG_TFM_FLASH_LAYOUT_NS_SIZE=0x40000

# Enable secure service for AES
CONFIG_TFM_CRYPTO=y
CONFIG_TFM_CRYPTO_AES=y
```

### 2. Rust Secure Partition (Secure World)

This code lives in `src/secure_partition.rs` and is compiled with `--target thumbv8m.main-none-eabihf`:

```rust
//! Secure partition: owns AES-256 key, never exposed to NS
#![no_std]
#![no_main]

use cortex_m_rt::entry;
use tfm_protected_storage::ProtectedStorage;
use tfm_crypto::aes256;

// Key stored in Secure flash, only accessible from S-world
const AES_KEY: &[u8; 32] = b"0123456789abcdef0123456789abcdef";

#[entry]
fn secure_main() -> ! {
    // Initialize TF-M secure services
    tfm::init().unwrap();

    // Store key in protected storage (tamper-resistant)
    let mut storage = ProtectedStorage::new();
    storage.write(b"aes_key", AES_KEY).unwrap();

    // Register secure function for NS to call via SVC
    tfm::register_secure_function(0x01, |input: &[u8]| -> Result<[u8; 16], ()> {
        let mut cipher = aes256::Cipher::new(AES_KEY);
        let mut output = [0u8; 16];
        cipher.encrypt_block(input.try_into().unwrap(), &mut output);
        Ok(output)
    });

    loop {
        // Wait for secure service requests
        tfm::wait_for_request();
    }
}
```

### 3. Non-Secure Rust Application (NS World)

In `src/main.rs` (compiled with `--target thumbv8m.main-none-eabihf` and `-C link-arg=-Wl,--cmse-implib`):

```rust
//! Non-secure application: calls secure partition via SVC
#![no_std]
#![no_main]

use zephyr::prelude::*;
use zephyr::sys::svc;

// Secure function ID 0x01: AES-256 encrypt
// The veneer is generated by TF-M build system
extern "C" {
    fn tfm_veneer_aes_encrypt(input: *const u8, output: *mut u8) -> i32;
}

#[entry]
fn main() -> ! {
    let plaintext = b"Hello, nRF54LM20!";

    // Call into Secure world via CMSE veneer
    let mut ciphertext = [0u8; 16];
    let ret = unsafe {
        tfm_veneer_aes_encrypt(plaintext.as_ptr(), ciphertext.as_mut_ptr())
    };

    if ret == 0 {
        println!("Encrypted: {:02x?}", ciphertext);
    } else {
        println!("Secure call failed: {}", ret);
    }

    loop {}
}
```

### 4. Build and Flash Commands

```bash
# Build the secure partition (TF-M + Rust)
west build -b nrf54lm20dk/nrf54lm20/cpuapp -d build_secure \
    -- -DCONFIG_TFM=y -DCONFIG_TFM_ISOLATION_LEVEL=2

# Build the non-secure application (Rust)
cargo build --target thumbv8m.main-none-eabihf --release

# Combine both images into a single flashable binary
west flash -d build_secure --runner nrfjprog \
    --hex-file build_secure/tfm/secure_fw.hex \
    --hex-file target/thumbv8m.main-none-eabihf/release/nonsecure.hex
```

## Common Pitfalls & Gotchas

1. **SAU region overlap**: If your SAU regions in the device tree overlap, the hardware takes the most restrictive. Double-check `nrf54lm20.dtsi` for default SAU regions—the nRF54LM20 has a fixed SAU region for the first 4 MB of flash. If your secure partition exceeds that, the NS world will fault on access. Always verify with `west build -t partition_manager_report`.

2. **Veneer table alignment**: The CMSE (Cortex-M Security Extensions) veneer table must be 32-byte aligned and placed in the Secure world's first 4 KB. If your Rust linker script doesn't place it correctly, the NS `BLXNS` instruction will trigger a SecureFault. Use `--cmse-implib` and check the generated `.cmse_veneer` section in the map file.

3. **Interrupt handling across worlds**: Non-secure interrupts cannot preempt secure code unless you explicitly configure the NVIC's security attribution. If you have a high-priority NS interrupt (e.g., radio), it will be masked while the S-world is executing. For real-time requirements, move the time-critical ISR into the Secure world or use the S-world's PendSV to defer work.

## Try It Yourself

1. **Extend the secure partition** to add a second secure function that returns the device's unique ID (UID) from the nRF54LM20's FICR registers. The NS world should only be able to read the UID, not write it.

2. **Add a secure boot check**: In the Secure world, verify a SHA-256 hash of the NS application before allowing it to run. Use Zephyr's `bootutil` library and the nRF54LM20's flash controller to read the NS image from flash.

3. **Measure the overhead**: Use a GPIO toggle in both the S-world and NS-world to measure the latency of a secure function call. Compare it to a direct function call. On the nRF54LM20 at 128 MHz, expect ~150-200 cycles for the SVC + veneer overhead.
